** Mas Tanenbaum enxergou o problema certo

Não era ``microkernel sempre vence''. Era sobre o *raio de explosão*:

| Monolítico | Microkernel |
|------------+-------------|
| drivers, FS, rede no modo privilegiado | mecanismo minimo no kernel |
| chamada de função barata | IPC explícito |
| falha pode comprometer o sistema | serviços isolados em user space |
| TCB enorme | TCB pequeno e analisável |

Separar serviços e comunicar por mensagens virou uma ideia central para
sistemas críticos. L4 mostrou que isso tambem poderia ser rápido.

\source{Heiser, COMP9242 W01/W08; \textcite{heiser2025whitepaper}}

** Linux entrega políticas; seL4 entrega mecanismos

#+begin_center
\begin{tabular}{c|c}

# Speaker (1:10): explique refinamento como ``C so faz o que o modelo permite''.

** Capability: uma referência com autoridade

Uma capability e um token inforjável mantido pelo kernel:

- aponta para um *objeto* (endpoint, frame, TCB, CNode...)
- carrega *direitos* (por exemplo, ler/escrever/conceder)
- ocupa um slot no *CSpace* do componente
- pode ser copiada, restringida, marcada (=badge=) e revogada

#+begin_center
\Large não ha cap $\Rightarrow$ não ha operação
#+end_center

Autoridade e conectividade sao dadas na construção do sistema, não descobertas
por um nome global ou por credenciais ambientes.

\source{Heiser, COMP9242 W01-2, slides 3--10; \textcite{heiser2025whitepaper}}

# Speaker (1:05): compare com file descriptor, mas destaque direitos e derivacao.

** Exemplo: chamar um servidor por endpoint

#+begin_example
Cliente A              seL4                 Servidor
slot 7: Endpoint cap   ---- Call() -------> ReplyRecv()
       rights: Write        mensagem
       badge: 0xA      <---- resposta ------
#+end_example

1. A so pode enviar porque possui a capability do endpoint.
2. O kernel entrega =badge 0xA=: o servidor identifica A sem confiar em um ID enviado.
3. =Mint= cria uma capability derivada, talvez somente =Write=.
4. =Revoke= remove toda a subarvore derivada dessa autoridade.

O kernel medeia a invocação; o servidor implementa a política.

\source{Heiser, COMP9242 W01-2, slides 4--9 \parencite{heiser2025course}}

# Speaker (1:00): seja claro sobre o status experimental.

** A camada LionsOS

Não e uma distribuição generalista: e um conjunto de peças combinaveis.

- *sDDF*: interfaces de drivers por classe de dispositivo
- *driver*: traduz hardware para filas; faz uma coisa
- *virtualiser*: multiplexa clientes, DMA e política
- *filas SPSC lock-free*: dados em memoria compartilhada
- *notificações Microkit*: sinalizam trabalho, sem copiar payload
- bibliotecas e componentes: musl libc, rede, storage, VMs

Arquitetura estática + separacao estrita = menos estado compartilhado e
componentes menores para raciocinar, substituir e recuperar.

\source{\textcite{heiser2025lionsos}; \textcite{velickovic2024lionsos}; \textcite{sddfdesign}}

** Microkit: a sintaxe da arquitetura

#+begin_src xml
<protection_domain name="beam_server">
  <map mr="beam_heap" perms="rw" />
</protection_domain>
<channel>
  <end pd="beam_server" id="4" />
  <end pd="timer_driver" id="1" />
</channel>
#+end_src

- *PD*: um ELF, uma thread, um espaco virtual fixo
- *memory region*: mapeamento explícito com permissões
- *channel*: notificacao ou chamada protegida entre dois PDs
- a ferramenta transforma a descrição estática em uma imagem bootavel

\source{Microkit User Manual \parencite{microkitmanual}}

# Speaker (1:05): o XML e ilustrativo; a topologia real de Chrysopolis e gerada em Zig.

** libmicrokitco: várias esperas, uma thread

Microkit oferece um loop de eventos por PD. Software POSIX espera poder bloquear.

#+begin_center
\Large várias cothreads cooperativas $\rightarrow$ uma kernel thread
#+end_center

- scheduler FIFO em user space
- uma cothread espera I/O; outra continua
- semaforos conectam eventos do =notified()= a quem estava bloqueado
- não cria paralelismo: organiza concorrência cooperativa dentro do PD

Para Chrysopolis, isso implementa a forma de =pthread= que o ERTS espera sem
inflar o modelo de threads do Microkit.

\source{README do libmicrokitco \parencite{libmicrokitco}; codigo de Chrysopolis, =src/runtime/process.c=}

* Chrysopolis: BEAM sobre a fundação verificada

** A peça que faltava era aberta

Ihor Kuz/Kry10 demonstrou a afinidade em 2022:

#+begin_center
\Large BEAM = prevenir + recuperar \\
\Large seL4 = conter
#+end_center

Mas o sistema Kry10 e sua integração não foram publicados como uma base aberta
e reproduzivel. *Chrysopolis nasceu dessa frustracao*: refazer publicamente a
ponte ERTS--seL4, agora sobre Microkit e LionsOS.

Objetivo: uma fundação verificavel para aplicações Erlang, Elixir e Gleam---não
alegar que o BEAM ou LionsOS inteiro ja estejam verificados.

#+begin_example
Gleam / Erlang / OTP
        ERTS 28.5

** Testar o impossível: bootar de verdade

#+begin_src shell
nix flake check -L
nix build .#checks.x86_64-linux.tcp-smoke -L
nix build .#checks.x86_64-linux.blk-restart-smoke -L
#+end_src

Onze testes sobem imagens reais no QEMU e inspecionam a serial:

- boot, Eshell, RNG, sockets e =gen_tcp= nos dois sentidos
- falha de um PD, restart com limite e =give up=
- restart de serial, timer, bloco e rede; servico deve continuar
- módulos Erlang de teste compilados com =warnings_as_errors=

Reprodutibilidade aqui inclui o experimento: entrada fixada, imagem bootavel e
critério observável.
