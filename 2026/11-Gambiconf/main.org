* 1992: Tanenbaum x Torvalds

** "Linux is obsolete"

Em 29 de janeiro de 1992, =comp.os.minix=:

#+begin_quote
*Andrew Tanenbaum*: Most older operating systems are monolithic, that is, the
whole operating system is a single a.out file that runs in "kernel mode". This
binary contains the process management, memory management, file system and the rest. (...)

The alternative is a microkernel-based system, in which most of the OS runs as
separate processes, mostly outside the kernel.  They communicate by message
passing.  The kernel's job is to handle the message passing, interrupt handling,
low-level process management, and possibly the I/O.

[cite: @tanenbaum1992linux]
#+end_quote

+ Linux: kernel monolítico, rápido, pragmático.
+ MINIX: microkernel, pequeno, portável e, sobretudo, didático.

** A provocação de Tanenbaum

#+begin_quote
*Andrew Tanenbaum*: While I could go into a long story here about the relative
merits of the two designs, suffice it to say that among the people who actually
design operating systems, the debate is essentially over. *Microkernels have
won*. (...)

Don't get me wrong, I am not unhappy with LINUX. *It will get all the people who
want to turn MINIX in BSD UNIX off my back*.

[cite: @tanenbaum1992linux]
#+end_quote

+ Linux era um passo de volta aos anos 1970.

** Linus ganhou (e com razão)

#+begin_quote
*Linus Torvalds*: (...) From a theoretical (and aesthetical) standpoint linux
looses. (...) *Linux wins heavily on points of being available now*.

[cite: @tanenbaum1992linux]
#+end_quote

#+ATTR_BEAMER: :overlay +-
+ O [[https://www.gnu.org/software/hurd/][GNU Hurd]] ainda não estava pronto, Linux estava.
  + Software facilmente disponível vence software perfeito.
+ Compatibilidade com Unix/POSIX trouxe aplicações e contribuidores.
+ Performance em hardware real importava mais que elegância.
+ E os microkernels da época (*Mach*) eram *lentos* pra caramba.

** On µ-Kernel Construction (1995)

*** Princípio da Minimalidade: 
:PROPERTIES:
:BEAMER_ENV: block
:END:

#+begin_quote
A concept is tolerated inside the microkernel only if moving it outside the
kernel, i.e. permitting competing implementations, would prevent the
implementation of the system's required functionality.

[cite: @liedtke1995construction p.2 part.2]
#+end_quote

#+ATTR_BEAMER: :overlay +-
+ O kernel é uma apenas uma /engine/ para fazer /context switching/.
+ Cada geração do L4 removeu mais coisas do kernel, e acabou ficando mais rápida.

** Scheduling Contexts (SCs)

*** Propriedades :BMCOL:B_block:
    :PROPERTIES:
    :BEAMER_col: 0.55
    :END:

#+ATTR_BEAMER: :overlay +-
+ O direito de usar a CPU: um /budget/ $B$ a cada /period/ $P$.
+ Um /TCB/ sem um /SC/ (ou sem /budget/) nunca será escalonado.
+ Pode ser "*doado*" em uma =Call=: um servidor passivo roda no tempo do
  cliente (~passive="true"~ no SDF).

# Mecanismo para isolamento temporal: budget = period funciona como uma fatia de tempo round-robin.

** sDDF: os /drivers/ já vêm prontos

+ Um protocolo padrão por classe de dispositivo: /driver/ $\rightarrow$
  /virtualiser/ $\rightarrow$ (/copier/) $\rightarrow$ cliente
  [cite: @sddfdesign].
+ Escrever um cliente é só falar com filas; nenhuma linha de código de hardware.

#+ATTR_LATEX: :font \small
| Classe sDDF          | No Chrysopolis            |
|----------------------+---------------------------|
| serial (UART)        | console do =Eshell=       |
| timer                | =erlang:monotonic_time()= |
| block                | módulos OTP (FAT)         |
| network              | =gen_tcp=                 |
| I2C, áudio, GPIO ... | não usamos                |

** O que o LionsOS já resolveu para nós

#+ATTR_LATEX: :font \small

** As exigências do ERTS

*** Propriedades :BMCOL:B_block:
